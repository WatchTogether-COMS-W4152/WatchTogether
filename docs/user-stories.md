# Group-management user stories

This iteration delivers a browser-based group-management increment. Watchlists, voting, progress tracking, and spoiler-free discussion remain future work. Each story has a stable Cucumber tag so it can be demonstrated and tested independently.

| Story                                        | User need and acceptance criteria                                                                                                                                                                                                                                                                                  | Executable coverage                                                                                                                                  |
| -------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------- |
| **US01 — Create my profile**                 | As a new viewer, I can register with my display name, email, and password so friends can recognize me. Registration signs me in. Invalid fields are explained, and differently cased versions of an existing email cannot create another account.                                                                  | `@US01`, [accounts.feature](../features/accounts.feature); User and registration RSpec coverage.                                                     |
| **US02 — Sign in and out**                   | As a registered viewer, I can sign in and sign out so my account stays private. Incorrect credentials fail. Logout revokes the session on the server, and expired or missing sessions return to sign-in.                                                                                                           | `@US02`, [accounts.feature](../features/accounts.feature); Session and authentication RSpec coverage.                                                |
| **US03 — Change my display name**            | As a viewer, I can update the name shown to friends. The change persists and appears in member lists. A rejected name leaves the previous name intact.                                                                                                                                                             | `@US03`, [accounts.feature](../features/accounts.feature); profile request specs and frontend form tests.                                            |
| **US04 — Create a private group**            | As a viewer, I can name a group and automatically become its first owner and member. A blank group name creates neither a group nor a membership.                                                                                                                                                                  | `@US04`, [groups.feature](../features/groups.feature); Group/Membership model and creation request specs.                                            |
| **US05 — View my groups and members**        | As a member, I can see the groups I belong to and their members' display names. My list excludes other groups, and knowing an unrelated group's URL grants no access.                                                                                                                                              | `@US05`, [groups.feature](../features/groups.feature), [invitations.feature](../features/invitations.feature); group request specs.                  |
| **US06 — Invite friends and replace a code** | As an owner, I can share a reusable code and replace it when necessary. Multiple friends can use the same current code. Old codes stop working immediately after replacement, and existing members remain.                                                                                                         | `@US06`, [invitations.feature](../features/invitations.feature); invitation request specs and owner-control frontend tests.                          |
| **US07 — Join through an invitation**        | As an invited viewer, I can paste a code to join. Whitespace and letter case are tolerated. Invalid codes grant no access. Repeated joins, including the owner's own code, do not duplicate membership. I must sign in first.                                                                                      | `@US07`, [invitations.feature](../features/invitations.feature); joining request specs and frontend form tests.                                      |
| **US08 — Protect private group information** | As a member, I can trust that other members cannot read my email, and only owners can see or replace invitation codes. Outsiders cannot read group details or change invitations.                                                                                                                                  | `@US08`, [groups.feature](../features/groups.feature), [invitations.feature](../features/invitations.feature); privacy and permission request specs. |
| **US09 — Delete a group I own**              | As an owner, I can delete a group I no longer need. The web interface asks for confirmation and lets me cancel. Deletion removes the group for everyone and disables its invitation, while keeping member accounts and other groups. Members and outsiders cannot delete it.                                       | `@US09`, [groups.feature](../features/groups.feature); deletion request specs and frontend confirmation/cancellation tests.                          |
| **US10 — Share ownership with a member**     | As an owner, I can make an existing member another owner so we can share responsibility. Confirmation explains that all owners can invite, manage members, and delete the group. Existing owners keep their roles, repeat promotion is harmless, and ordinary members and outsiders cannot promote anyone.         | `@US10`, [memberships.feature](../features/memberships.feature); membership request specs and frontend management/confirmation tests.                |
| **US11 — Remove someone from my group**      | As an owner, I can remove another member, including another owner, after a named confirmation. Their access ends and the invitation changes; accounts, other groups, and remaining memberships are kept. I cannot remove myself, so the group keeps an owner. Ordinary members and outsiders cannot remove anyone. | `@US11`, [memberships.feature](../features/memberships.feature); membership request specs and frontend removal/cancellation tests.                   |

Run all acceptance stories with `bundle exec cucumber`, or just a story with `bundle exec cucumber --tags @US06`. Cucumber sends real HTTP requests into Rails using separate cookie jars for different viewers. Scenarios are isolated with database transactions and cleared rate-limit state. No application behavior is mocked. React component tests and the manual browser demonstration cover the frontend separately.

RSpec also checks details that are not useful as user-facing story steps: database uniqueness, role constraints and foreign keys, rollback of failed group creation, password/session digests, cookie settings, CSRF handling, throttling, and excluded sensitive fields. The corresponding request suites are [authentication](../spec/requests/authentication_spec.rb), [profiles](../spec/requests/profiles_spec.rb), [groups and invitations](../spec/requests/groups_spec.rb), and [membership management](../spec/requests/memberships_spec.rb); model constraints are tested under [spec/models](../spec/models). SimpleCov enforces at least 90% Rails application line coverage; [verification.md](verification.md) records measured runs.

## Two-user demonstration

Use the running app in two separate browser profiles or one regular and one private window. Use temporary demo accounts with different email addresses. Do not use a production database for destructive testing.

1. **Alice:** Open the app and choose **Create account**. Register with a display name, email, and password. Confirm the groups page opens automatically and displays its empty state.
2. **Alice:** Open **Create group**, submit a blank name to see validation, then create **Friday Night**. Confirm Alice is the owner and appears once in the member list.
3. **Alice:** Copy the group's invitation code. Keep this original code for step 8.
4. **Bob:** In the second browser session, register another account. Open **Join group**, try an invalid code, then paste Alice's code. Confirm Friday Night opens with both names.
5. **Bob:** Return to **My groups** and reopen Friday Night. Confirm Bob sees the member list but no invitation code or reset control. Join with the same code again and confirm Bob still appears once.
6. **Bob:** Open **Profile**, change the display name, refresh, and confirm the new name remains. Refresh Alice's group page and confirm the member list uses Bob's updated name.
7. **Bob:** Sign out. Confirm visiting `/groups` or `/profile` returns to sign-in. Sign in again and confirm the group membership remains.
8. **Alice:** Replace the invitation code. Confirm it changes and Bob remains a member. **Bob:** Try joining with the saved original code and confirm it is rejected; joining with the new code succeeds without a duplicate membership.
9. **Bob:** Create a separate group. Copy its URL. **Alice:** Open that URL while signed in and confirm a not-found page protects Bob's private group.
10. Refresh both sessions and inspect browser/server logs for unexpected errors. Confirm the layout remains usable at a narrow browser width.
11. **Alice:** Open **Manage** on Bob's row and choose **Make owner**. Read the permissions explanation and cancel; Bob should remain an ordinary member. Repeat and confirm. Both names should now have an **Owner** badge. **Bob:** Refresh Friday Night and confirm invitation and management controls appear. **Alice:** Confirm you remain an owner too.
12. **Alice:** Open **Manage** on Bob's row and choose **Remove from group**. Confirm the warning names Bob, identifies his owner role, and explains that the invitation will change. Cancel and verify both members remain. Save the current code, repeat, and confirm removal. Bob should disappear from Friday Night, and the code should change. There should be no **Manage** control on Alice's own row.
13. **Bob:** Refresh Friday Night and confirm access is denied. Confirm Friday Night is absent from **My groups**, Bob's separate group remains, and the saved code is rejected by **Join group**. **Alice:** Share the new code. **Bob:** Join again and confirm you return as an ordinary member without invitation or management controls.
14. **Alice:** On the temporary Friday Night group, choose **Delete group**, then cancel and confirm the group remains. Open the confirmation again and confirm deletion. Both viewers' group lists should lose Friday Night; its previous URL and invitation should no longer work. Both accounts and Bob's separate group should remain available.

The account, group, and membership changes persist in the configured database. Browser storage alone is not the source of truth. Session-expiry timing and replay of a revoked cookie are covered by automated tests rather than waiting 30 days during the demonstration.

Group management intentionally separates shared ownership from leaving or demotion. Owners cannot remove themselves, and there is no owner-demotion control in this iteration. Removing someone is not a permanent ban: sharing the replacement invitation allows them to join again as an ordinary member.
